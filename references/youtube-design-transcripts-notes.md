## 1. Figma Config 2024 — "Design systems best practices"
**Channel:** Figma · **URL:** https://www.youtube.com/watch?v=MJTCfSFLUGE
**Confidence:** high (clear talk audio, coherent transcript)

Per this talk, concrete design-systems-process advice:

- **Variants vs. component properties is a real tradeoff, not just a technical choice.**
  Variants group visually-related states of one component (e.g. button states/sizes)
  and are best when the states are mutually exclusive and few; component properties
  (boolean/instance-swap/text) scale better once a component has many independent,
  combinable dimensions — mixing too many variant permutations explodes the component
  set and makes the library hard to navigate. The presenters frame this as: reach for
  variants first for simple exclusive states, reach for properties once you have more
  than a couple of independent toggles.
- **Variable scoping should match intent, not convenience.** Scoping a color/number
  variable narrowly (e.g. to "corner radius" or to a specific property) prevents
  accidental misuse in a context the variable was never designed for, and this
  discipline is what keeps a design system's variable set trustworthy as it grows.
- **Code syntax mapping (Figma variables ↔ code tokens) is treated as core system
  infrastructure, not a nice-to-have.** Making sure each Figma variable declares its
  corresponding code token name is what lets designers and engineers stay in sync
  without a manual translation step, and is called out as one of the highest-leverage
  investments a systems team can make.
- **Design system health should be measured on both breadth and depth**, not adoption
  alone: breadth = how many teams/products use the system; depth = how much of a given
  product's surface is actually built from system components versus one-off, bespoke
  UI. A system can look "adopted" by breadth while still being shallow in depth, and the
  talk argues both numbers should be tracked and reported, not just breadth.
- **Governance and deprecation need an explicit process.** Components/tokens that are
  deprecated should have a clear migration path and a sunset timeline communicated to
  consuming teams — silently removing or changing shared components erodes trust in the
  system faster than almost anything else, per the speakers.

## 2. Figma Config 2025 — "Building design systems together"
**Channel:** Figma · **URL:** https://www.youtube.com/watch?v=kq_lqeIIkPw
**Presenters:** Jake Albaugh & Chad Bergman · **Confidence:** high

Per this talk:

- **A design system is a collaboration surface, not just a component library.** The
  talk frames the system's real value as reducing the coordination cost between
  designers and engineers working in parallel — the library is the artifact, but the
  goal is shared vocabulary and shared source of truth across both disciplines.
- **Design system teams should treat their own consumers (product teams) like
  customers**, actively soliciting feedback and treating friction reports as product
  signal rather than as noise to be defended against.
- **Adoption is a change-management problem as much as a design problem** — getting an
  existing, mature product to migrate onto a new/updated system component takes
  deliberate rollout planning (staged migration, clear communication of what breaks and
  why), not just publishing the update and expecting teams to pick it up.
- **Cross-functional documentation (usage guidance, not just visual specs) is what
  actually prevents misuse** of shared components in the field — a component with only
  a visual spec and no "when to use this / when not to" guidance gets misapplied.

## 3. Figma Config 2024 — "How we redesigned Figma" (the "UI3" redesign)
**Channel:** Figma · **URL:** https://www.youtube.com/watch?v=qYvLEr2jml4
**Presenters:** Ryan, Joel, Casey · **Confidence:** high

Per this talk, principles behind Figma's own UI3 interface redesign:

- **Stability by default**: panels and UI chrome should not rearrange themselves or
  jump around as a user works — a tool used for hours a day needs a UI that stays
  spatially predictable, even when that means resisting an "optimal" per-context layout
  in favor of a consistent one.
- **Minimize chrome to maximize canvas/content.** The redesign's core motivation was
  reducing how much of the screen is UI framing versus actual work surface — every
  panel, toolbar, and border was scrutinized for whether it earned its pixels.
  Non-essential chrome collapses/hides until the moment it's actually needed.
- **Group related controls by task, not by feature category.** The team reorganized
  toolbar/panel groupings around what a user is actually trying to do in the moment
  (e.g. "adjusting appearance" vs. "adjusting layout") rather than by which engineering
  team owns the feature — a reminder that information architecture in a complex tool
  should follow the user's mental model of their task, not the org chart behind the
  product.
- **A redesign of this scale needs its own internal dogfooding discipline** — the team
  described extended internal-only testing periods specifically to catch muscle-memory
  regressions (things that "look better" but break an experienced user's learned
  shortcuts) before shipping broadly.

## 4. Figma Config 2025 — "Building the next computing platform" (fireside chat with Meta's spatial-computing lead)

**Confidence:** medium-high (clear conversational audio, but content is more tangential

Per this fireside chat, design-relevant points on AI and spatial-computing interaction
design:

- **Interaction design for spatial/AI interfaces has to design for ambiguity of intent**
  — unlike a 2D screen where a click target is unambiguous, voice/gesture/gaze-driven
  interfaces require the system to infer intent from imprecise signals, which pushes
  more design responsibility into fallback/disambiguation states rather than the
  "happy path" alone.
- **The speaker argues AI tooling lowers the floor for execution but does not by itself
  raise the ceiling of creative quality** — a sentiment echoed independently in the 2026
  keynote below (see #5), suggesting it's a real, recurring theme in Figma's current
  thinking rather than a one-off talking point.
- **Designing for "the next computing platform" (spatial/wearable) requires rethinking
  affordances from scratch** rather than porting flat-screen UI conventions directly —
  concepts like a persistent toolbar or modal dialog don't translate cleanly to a
  spatial context and need new interaction primitives.

Per this keynote, several concrete product-philosophy points relevant to design
process rather than just feature announcements:

- **"Code is a material for design, not the opposite of design"** — Dylan Field frames
  the long-running "design vs. code" debate as a false binary; the keynote's thesis is
  that code should be treated as one moldable design material alongside vectors,
  gradients, and type, not a separate downstream discipline design hands off to.
- **Collaborative exploration beats parallel-solo iteration.** The team explicitly
  calls out a failure mode of current AI-coding workflows: individual designers/
  engineers go "hundreds of prompts deep" alone with their own agents, then only
  compare results after the fact via recordings — losing the side-by-side, real-time
  comparison that made earlier (vector-based) Figma collaboration valuable. Their
  design response (putting code on the canvas, side-by-side variant comparison,
  option-drag branching) is a direct attempt to restore that "jam together" quality
  to a new material (code).
- **Design tools should let you compare many divergent explorations side-by-side before
  committing** — repeated as a principle across multiple segments (comparing code
  variants, comparing shader effects, comparing motion timing) — the throughline is
  that early-stage divergent exploration needs cheap, fast comparison, not sequential
  one-at-a-time evaluation.
- **"AI lowers the floor. It has not been clear yet that it also raises the ceiling of
  creativity — that's on designers, not tools"** — stated close to verbatim as the
  keynote's framing device, and echoed in the Meta fireside chat (#4), suggesting this
  is a considered, recurring Figma thesis rather than a throwaway line.
- **A design system principle stated directly**: contrast between rigid on-grid
  structure and one deliberately broken/expressive element is called out favorably in
  the "shaders" demo segment — restraint on the base grid, one signature expressive
  move layered on top, rather than decorating everything equally.

## 6. AJ&Smart — "What is a Design Sprint?"
**Channel:** AJ&Smart (video hosted by Christine Maji) · **URL:** https://www.youtube.com/watch?v=2PUsMiXuU4o
**Confidence:** high

Per this video, the canonical AJ&Smart/Jake Knapp five-day design-sprint structure:

- **A design sprint compresses the full design process (idea → prototype → test →
  learn) into five days** specifically to de-risk a product/feature decision before
  months of build investment — the value proposition is speed-to-real-answer, not
  speed for its own sake.
- **Day-by-day structure**: Monday = map the problem and pick a specific target/goal for
  the week (explicitly not solving yet, just scoping); Tuesday = individual sketching
  and idea generation, informed by looking at competitor/inspiration examples; Wednesday
  = the group reconverges, clusters ideas into themes, and votes to converge on a single
  concept to build; Thursday = build a prototype of only the pieces needed to test the
  concept (not a fully functional product); Friday = user-test the prototype with real
  users and capture what was learned.
- **The output of a sprint is not just a prototype — it's clarity on what to do next**:
  continue building the validated idea, discard and restart if the concept failed, or
  discover the original problem framing itself was wrong. All three outcomes are framed
  as valid, useful results of the week.
- **Sprints work best as genuinely cross-functional exercises** — not just designers,
  but engineering, the person who owns the underlying problem, and sometimes clients/
  customers in the room together, because the diversity of perspective is what produces
  solutions no single-discipline team would reach alone.

## 7. AJ&Smart — "Design Sprint 2.0: Prototyping Day Tips"
**Channel:** AJ&Smart (hosted by Dee) · **URL:** https://www.youtube.com/watch?v=s_mCidFnia0
**Confidence:** high

Per this video, five concrete tips for running prototyping day (Thursday) of a design
sprint:

1. **Give the prototyping team a dedicated, undisturbed space.** Interruptions/
   shoulder-looks break the focus needed to build fast under a tight deadline.
2. **Prioritize which sketched screens/steps actually need to be built.** Not every
   storyboard cell deserves equal build effort — identify the two or three key screens
   that carry the test's core question and focus effort there.
3. **Timebox each piece of the prototype explicitly** based on its importance — key
   screens get more time allocated than supporting screens, decided up front, so the
   team doesn't run out of the day mid-build.
4. **Schedule specific check-in windows** (e.g. just before lunch, and a couple of hours
   before end of day) rather than allowing ad hoc drop-ins — this protects focus time
   while still giving the team structured feedback moments.
5. **The single biggest misconception about "prototype" in a design sprint**: it does
   not mean a rough full-scale version of the whole product. It means only the specific
   pieces of the storyboard needed to test the idea — explicitly warns against adding
   "necessary-feeling" extras like login screens or settings screens that weren't part
   of what's being tested, because that scope creep both wastes the day and can
   contaminate what the user test is actually measuring.

## 8. AJ&Smart — "How Might We" (design sprint / design thinking exercise)
**Channel:** AJ&Smart (hosted by Brittany) · **URL:** https://www.youtube.com/watch?v=sRGk5oKXgCk
**Confidence:** high

Per this video, on the "How Might We" (HMW) note-taking technique:

- **HMW standardizes note-taking during open-ended stakeholder/user conversations** by
  converting whatever is being said — complaints, wants, rambling ideas — into a
  consistent "How might we ___?" phrase written on a sticky note, so a room full of
  people with different note-taking styles produces comparable, mergeable output.
- **The technique's real function is reframing a stated problem as an opportunity.**
  Rather than transcribing a complaint verbatim (e.g. "we don't get enough weekend
  traffic"), the listener actively translates it to the underlying opportunity ("how
  might we increase weekend usage of the space?") — this is framed as an active-
  listening and synthesis skill, not passive transcription.
- **Practical mechanics**: one sticky note per HMW statement, "HMW" written in the
  corner for scannability, generated live while listening to an unstructured monologue
  or interview, so that by the end of the conversation the team has a pile of
  individually-votable, individually-clusterable opportunity statements instead of a
  page of raw notes.

## 9. AJ&Smart — "Design Sprint 2.0: Storyboarding Hack" (User Test Flow)
**Channel:** AJ&Smart (hosted by Brittany, exercise led by Michael) · **URL:** https://www.youtube.com/watch?v=y5pSBgQUezQ
**Confidence:** high

Per this video, the "User Test Flow" hack for making storyboarding sessions faster and
more focused:

- **Problem being solved**: once a team has voted on a winning concept, moving straight
  into open storyboarding often turns into unstructured, meandering discussion where
  excited teammates push new ideas into the storyboard, eroding the alignment the sprint
  had just built.
- **The exercise**: each team member privately writes exactly six sticky notes, each one
  a single discrete user action step (a click, tap, or read) needed to move through the
  prototype toward the sprint's test goal — written like panels of a comic book, one
  action per note. A good technique for writing them: decide the first action and the
  last action first (using the sprint's map and target question as reference), then fill
  in the middle steps.
- **Each person reads their six-step flow aloud in turn** (the decider goes first or
  last, to hear everyone else's version before or after forming their own judgment).
- **Dot-voting selects a baseline flow**: everyone gets one vote on any row (including
  their own); the decider gets two votes — one to confirm the baseline flow, one to pull
  in an interesting step from a different row that's worth incorporating.
- **Payoff**: because the winning flow's steps are already agreed upon before drawing
  begins, the subsequent storyboard session (placing the winning sticky notes directly
  into the storyboard's empty cells) is reported to shrink from as long as a full
  afternoon (up to ~3 hours) down to roughly 1.5 hours, because the sequencing
  discussion has already happened.

## 10. The Futur — "Live Design Critique w/ Chris Do" (Facebook Live portfolio review)
**Channel:** The Futur · **URL:** https://www.youtube.com/watch?v=y1QzpLFgtqA
**Confidence:** medium — live, informal, multi-speaker audio with cross-talk; auto-
captions are readable and the substance is clear, but exact wording in fast exchanges is
less reliable than the scripted-talk transcripts above.

Per this live portfolio-review session, Chris Do's recurring critique points across
several real portfolios reviewed:

- **Thumbnails are the actual first design decision that matters.** On platforms like
  Behance/Dribbble, a browsing viewer's attention span is very short — a project's
  thumbnail needs to read clearly and specifically (e.g. show a branding application,
  not just an isolated logo mark) or the work gets skipped before it's even opened.
- **Show application/context before (or instead of) the isolated logo mark.** Do
  repeatedly recommends leading a case study with the logo applied in context (signage,
  packaging, business card) rather than the naked logotype, because applied context is
  what proves the mark actually works and is more visually enticing to a scanning
  viewer.
- **"Above the fold" still applies to portfolio pages.** If the first visible section of
  a case study doesn't capture interest, most viewers won't scroll further — so the
  strongest material (not sketches/process) should load first, with process/sketches
  placed later as a "reveal," not up front.
- **Title/label your work for discoverability and specificity**, not vague category
  names — "logo and identity design" beats an ambiguous project title, because titles
  function as search/scan cues for a buyer looking for a specific skill.
- **Curate ruthlessly — cut weaker pieces rather than show everything.** When some
  lettering/logo pieces in a set are clearly stronger than others, Do's advice is to
  remove the weaker ones rather than let them drag down the perceived skill level of the
  whole portfolio ("if I like some more than others, I'd suggest you edit out the ones
  that are not as good").
- **Great mockups sell design work**, and they don't need to be self-made — using
  purchased/stock mockup templates is presented as a legitimate, time-saving choice, not
  a shortcut to be ashamed of.
- **On sketches specifically**: sketches presented as part of a case study should show
  filled/solid form, not just line work, because logos and symbols are ultimately about
  solid shape relationships, not the linework used to arrive at them — Do demonstrates
  this live by filling in a traced sketch outline to show the difference.
- **Business/career advice given alongside the visual critique**: a designer struggling
  to find local demand should market to buyers where they already congregate online
  (Behance/Dribbble) rather than relying on a personal site alone, since buyers aren't
  searching for a specific individual by name.

## 11. The Futur — "How To Improve Your Layout and Typography" (live critique)
**Channel:** The Futur · **URL:** https://www.youtube.com/watch?v=xjAQ5CK4oqg
**Confidence:** medium — long (~90-minute) live multi-speaker critique with cross-talk
and some off-topic banter interspersed; auto-captions are legible and the design
substance below is clearly stated, but this is the least polished/scripted source in
this set and some phrasing has been paraphrased for clarity rather than quoted.

Per this live typography/layout critique session (Chris Do with co-host Molly,
critiquing several submitted posters), recurring, generalizable principles:

- **When a layout "feels off" and you can't articulate why, strip it back to nothing
  and rebuild it one element at a time.** Do repeatedly uses this technique live: hide
  every layer, confirm the base composition (color field + primary type) reads well on
  its own, then reintroduce elements one at a time, evaluating after each addition
  whether it helps or hurts — rather than trying to fix a cluttered layout by tweaking
  everything simultaneously.
- **"Everything looks better smaller" as a recurring, semi-joking but genuinely-meant
  rule** — oversized type/elements read as cramped because they leave no negative space;
  scaling an element down (even one that seems too small at first) often reads as more
  confident and better-balanced, the same way a large piece of furniture makes a room
  feel small.
- **Contrast is named directly, more than once, as the most important compositional
  tool** ("what's the most important rule of composition? Contrast," stated by a guest
  designer and affirmed by Do) — used specifically to establish a clear primary/
  secondary/tertiary reading order (what should be read first, second, third) rather
  than having multiple elements compete at the same visual weight.
- **Reduce simultaneous typeface/weight variation.** A poster with too many different
  typefaces and case treatments (serif italic + sans-serif upper/lower + all-caps +
  a fourth display treatment) was diagnosed as the source of a layout "not working" even
  though the designer couldn't initially articulate why — the fix demonstrated was
  consolidating to fewer typefaces and letting one element (a striking custom/photographed
  letterform) be the clear visual hero rather than competing with several others.
- **Alignment should be deliberate and tied to a reference axis** — not just the default
  baseline-left convention. Do explicitly demonstrates rotating a type block onto a new
  (non-horizontal) axis as a legitimate secondary alignment strategy when the default
  axis isn't working, cautioning that new axis has to be committed to and integrated
  rather than left half-resolved.
- **Italics exist historically to fit more text per line/page (typesetting economy), not
  primarily as a design "emphasis" device** — and applying italic to an entire block
  defeats its own purpose as emphasis, since emphasizing everything emphasizes nothing;
  Do recommends reserving italic for genuine, sparing emphasis.
- **Decorative/non-functional elements are acceptable in service of visual interest, but
  should still relate to something in the composition** (grid, other shapes, or content
  meaning) rather than being arbitrary — a stray circular element with no compositional
  or conceptual link to the rest of the piece was flagged as the weakest part of one
  submission specifically because it "relates to nothing."
- **When two elements need to feel connected across a layout (e.g. a front-cover element
  and a back-cover element on a brochure), use repeated visual devices (a matching rule
  line, a matching color bar) to imply the relationship**, even subconsciously to the
  viewer — treat a multi-page piece as one continuous three-dimensional object, not
  independent pages.
- **Reduce redundancy in text emphasis** — if two words say close to the same thing (e.g.
  "the hustle" / "the grind" with a redundant connecting word), cutting the redundant
  word and overlapping/relating the two remaining words visually (e.g. via transparency/
  registration) can strengthen the concept rather than just shortening the copy.
- **Color used sparingly reads as more premium than color used everywhere** — explicitly
  called out with a gold accent color ("you can over-gold everything... use it very
  sparingly and thoughtfully") as a direct, generalizable warning against overusing an
  accent color once it's been established as effective in one spot.

**On this collection as a whole**: across the Figma talks (#1, #2, #3, #5) a clear,
consistent thesis about design-systems maturity emerges — systems succeed on
adoption breadth *and* depth, on explicit governance/deprecation process, and on
tight design/code token mapping, not on visual component coverage alone. Across the
AJ&Smart sprint videos (#6–#9), the throughline is that structure and constraint
(timeboxing, six-action-step limits, dot-voting, dedicated focus space) are what make
a compressed five-day process actually work, rather than loosening structure to "make
room for creativity." Across the two Futur critique sessions (#10, #11), Chris Do's
critique method is consistently: identify what the eye reads first/second/third,
reduce competing elements until one clear hero emerges, and question every element's
right to be there rather than only adding polish.
